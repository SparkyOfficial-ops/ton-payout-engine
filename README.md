# ton-payout-engine

Шлюз массовых выплат TON. Пачку отправляет `CtonChainSender` через соседний `cton-sdk`.

Из SDK используются только:

- `com.cton.api.TonApiClient` — баланс и `sendBoc`
- `com.cton.contract.HighloadWallet` — сборка и подпись Highload Wallet v2
- `com.cton.contract.BulkTransfer` — один получатель внутри пачки
- `com.cton.sdk.Address` и `com.cton.sdk.Crypto.PrivateKey` — адрес и ключ Ed25519

`Cell` и `CellBuilder` используются, чтобы собрать тело Jetton `transfer`. `Boc` и `HashmapE` остаются внутри `HighloadWallet`. Нативная библиотека `cton-sdk-core` нужна в момент подписи. Класс `Jetton` из SDK и кошельки V3/V4 этот сервис не вызывает.

## Запуск

```text
mvn -f ../cton-sdk-main/pom.xml install -DskipTests
mvn clean package
java -jar target/ton-payout-engine-0.1.0-SNAPSHOT.jar
```

`package` кладёт зависимости в тот же JAR. Подпись при старте грузит нативную `cton-sdk-core`: на Windows это `cton-sdk-core.dll`, в Linux-образе `libcton-sdk-core.so`.

Образ собирается из этого репозитория. Во время сборки он сам клонирует `cton-sdk-main`:

```text
docker build -t ton-payout-engine .
```

GitHub Actions на каждый push и pull request ставит тот же SDK, гоняет `mvn test` и собирает образ. Ветка `main` публикует его в GHCR: `ghcr.io/sparkyofficial-ops/ton-payout-engine`.

Контейнеру нужны `WALLET_ADDRESS`, читаемый файл ключа по `WALLET_KEY_PATH` (в образе это `/secrets/wallet.key`) и `PAYOUT_API_KEY`. База пишется в том `/data`.

Ключ API задаётся переменной `PAYOUT_API_KEY` (или `auth.apiKey` в `src/main/resources/application.properties`). Файл ключа кошелька лежит только на сервере, путь — `WALLET_KEY_PATH`. В репозиторий его не класть.

## API

Заголовок: `X-Api-Key`. Для выплаты обязателен `X-Idempotency-Key`: уникальный id операции на стороне бота. Повтор с тем же ключом и тем же телом не создаёт вторую пачку и возвращает текущий статус (`200`). Другое тело с тем же ключом отвечает `409`.

`POST /api/v1/payout`

```json
{
  "transfers": [
    {"to": "EQ...", "amount": "5", "comment": "vasya"},
    {"to": "EQ...", "amount": "2", "comment": "petya"},
    {"to": "EQ...", "amount": "10", "comment": "masha"}
  ]
}
```

`amount` — сумма в TON. `currency` может быть `TON` (по умолчанию) или `USDT`. Для USDT у `amount` не больше 6 знаков после запятой: `1.5` хранится как `1500000`. `amountNano` принимается, если сумма уже в минимальных единицах: наноTON или базовые единицы USDT. Выплата USDT — это внутреннее сообщение на `USDT_JETTON_WALLET` (Jetton-кошелёк отправителя) с телом `op::transfer` `0x0f8a7ea5`, получателем в payload и прикреплённым газом `USDT_GAS_NANO` (0.05 TON). Без `USDT_JETTON_WALLET` такой запрос отвечает `400`. Ответ `202` содержит `batchId`. Адрес проверяется до записи в базу: user-friendly base64url с CRC16 или raw `workchain:64hex`, workchain от -128 до 127. На `mainnet` friendly-адрес с битом testnet (`kQ` / `0Q`) тоже даёт `400`: туда не уходят боевые TON. Опечатка не попадает в общий батч. Уже сохранённая битая заявка помечается `failed` одна, соседние переводы этого окна уходят как обычно.

Перед ответом переводы записываются в SQLite (`PAYOUT_DB_PATH`, по умолчанию `data/payout.db`) со статусом `queued`. После перезапуска такие переводы снова попадают в автобус. Статус `sending` означает, что отправка уже началась: эти строки после падения процесса сами не отправляются повторно. Хэш внешнего сообщения считается локально и записывается в базу до `sendBoc`. Если узел ответил ошибкой, те же байты отправляются ещё два раза. Обрыв соединения, HTTP 429, 500 или другой 5xx после этих трёх попыток не бросает пачку на 16 минут: то же подписанное сообщение пробуется снова через `PAUSE_RETRY_MS`. Новая подпись не создаётся. Если процесс умрёт, пока байты уже в сети, пачка остаётся `sending` с этим хэшем, а не `failed`.

Один `POST /api/v1/payout` — это одна транзакция Highload Wallet. Больше `BATCH_MAX_SIZE` переводов (254) даёт `400`, и в базу ничего не пишется: иначе часть людей получит TON, а весь запрос станет `failed`. Несколько запросов одного окна уходят вместе, только если каждый помещается целиком. Движок копит их `BATCH_WINDOW_MS` (по умолчанию 2500 мс) или до 254 и отправляет одной транзакцией Highload Wallet v2. Хэш из `sendBoc` означает только приём в мемпул: пачка становится `sent`. Через `CONFIRM_DELAY_MS` (по умолчанию 12 секунд) фоновый опрос один раз за тик забирает последние 100 транзакций `getTransactions`. Если хэша там нет, следующая страница начинается с `lt` и `hash` последней транзакции и идёт дальше, пока транзакции не станут старше `MESSAGE_TTL_MS`. Этот список общий для всех ожидающих пачек тика. Если хэш входящего сообщения есть в блоке, статус становится `confirmed`. В `query_id` внешнего сообщения записывается срок на минуту короче `MESSAGE_TTL_MS`: по умолчанию сообщение живёт 15 минут. Опрос не ставит `failed`, пока эти 16 минут не прошли, даже если хэша ещё нет в `getTransactions`. Пустой `sent_at` считается от `created_at`: каждый промах опроса больше не обнуляет срок. Иначе бот повторит выплату, а первое сообщение позже попадёт в блок.

Вебхук на `sent` уходит сразу. `confirmed` и `failed` записываются в `webhook_events` в той же транзакции, что и статус пачки. Фоновый поток отправляет сохранённый JSON, пока клиент не ответит 2xx. После ошибки повтор через 5 с, 30 с, 2 мин и дальше каждые 10 мин. Если процесс остановится после ответа клиента и до отметки `delivered`, тот же JSON уйдёт ещё раз:

```json
{"batchId":"...","status":"confirmed","count":3,"txHash":"...","error":null}
```

`GET /api/v1/status/{batchId}` показывает `queued`, `sending`, `paused`, `sent`, `confirmed` или `failed` и массив `transfers`: у каждого перевода `to`, десятичный `amount` и его `status`.

Перед отправкой движок сравнивает баланс TON с суммой TON-переводов, газом USDT и комиссией сети: `FEE_RESERVE_NANO` (0.05 TON на внешнее сообщение) и `FEE_PER_TRANSFER_NANO` (0.008 TON на каждое внутреннее). Для 254 переводов TON это 2.082 TON, а не 0.05. Сумма USDT в эту проверку не входит: на каждый такой перевод добавляется только `USDT_GAS_NANO`. Если TON меньше, пачка становится `paused`, в сеть ничего не уходит, и на `ALERT_URL` отправляется алерт. Проверка повторяется через `PAUSE_RETRY_MS`.

При старте `recovery.sweep()` сразу проверяет все пачки в `sending`: хэш, который уже лежит в блоке, становится `confirmed` без ожидания `SENDING_STALE_MS`. Эти пачки не отправляются снова. Если хэша в блоке ещё нет, проверка повторяется, пока не выйдет `MESSAGE_TTL_MS`; только тогда пачка становится `failed`. Повтор такой выплаты делается новым `X-Idempotency-Key`, а если хэша не было — сначала сверяется история кошелька. Фоновый опрос и `POST /api/v1/recovery` по-прежнему не трогают `sending` младше пяти минут, чтобы не пересечься с отправкой, которая идёт в этом процессе.

Раз в сутки пачки `confirmed` и `failed` старше `HOUSEKEEPING_RETENTION_MS` (30 дней) переносятся из `payout.db` в соседний `payout-archive.db`. `queued`, `paused`, `sending` и `sent` остаются на месте. Тот же `X-Idempotency-Key` после архивации возвращает прежний статус и вторую выплату не создаёт. История пачки остаётся в архиве. Уже доставленные строки `webhook_events` для этих пачек удаляются, а ещё не доставленные остаются и продолжают повторяться.

`GET /api/v1/balance`

`GET /health` без ключа. Ответ `200`, когда `SELECT 1` к SQLite проходит и на месте адрес с файлом ключа. Если база недоступна или ключ пропал, ответ `503`: Docker и Kubernetes не пускают на процесс трафик. Запросы принимает пул из 16 потоков, поэтому проверка здоровья не ждёт ответ ноды на `/api/v1/balance`.

`GET /metrics` тоже без ключа и отдаёт OpenMetrics: `payout_queue_size`, `wallet_balance_nano`, гистограмму `batch_processing_duration_seconds` (от приёма пачки до попадания в блок) и счётчик `toncenter_errors_total`. Логи идут в stdout одним JSON-объектом на строку. У строк, которые относятся к одной пачке, есть поле `batchId`.

Нужны `WALLET_ADDRESS` и файл ключа (`WALLET_KEY_PATH`: 32 байта, 64 hex-символа, base64 или мнемоника). Ключ читается при старте: он должен подписывать, а адрес Highload Wallet v2 из этого ключа и `WALLET_SUBWALLET_ID` должен совпасть с `WALLET_ADDRESS`. Иначе процесс завершается до приёма API, и `202` за битый ключ не отдаётся. `txHash` — это hash внешнего сообщения из ответа TON Center `sendBoc`. Подтверждение сравнивает его только с `in_msg.hash` или `in_msg.body_hash`. Hex от SDK и base64 от Toncenter — это одни и те же 32 байта. `transaction_id.hash` вместе с `transaction_id.lt` — только курсор следующей страницы `getTransactions`, не хэш сообщения. В лог пишется сырой JSON первой транзакции из `getTransactions` и обе строки `in_msg`, чтобы их можно было сверить с хэшем `cton-sdk` посимвольно.
