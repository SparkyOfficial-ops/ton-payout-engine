ton-payout-engine

Highload TON payout gateway. Sends batches of up to 254 transfers in a single Highload Wallet v2 transaction. Built on cton-sdk — Java 17, zero frameworks.

Download JAR  v1.0.0   Source

Highload Wallet v2

Up to 254 transfers in one transaction. Signed locally via cton-sdk native library.

Batch Window

Collects requests for BATCH_WINDOW_MS (default 2500 ms) before sending, reducing fees.

Idempotency

Pass X-Idempotency-Key on every request. Duplicate calls return the same batch status.

TON & USDT

Native TON transfers or Jetton USDT with auto-computed gas. Set currency: USDT in the request.

Auto-retry

Same signed bytes retried on 5xx / 429 / timeouts. No re-sign, no double-spend.

Webhooks

Persistent outbox delivers sent, confirmed, failed events with exponential back-off.

OpenMetrics

GET /metrics exposes queue size, wallet balance, batch latency histogram and error counter.

SQLite + Archive

All batches persist in SQLite. Records older than 30 days move to payout-archive.db automatically.

How it works

  1. 1 Your bot calls POST /api/v1/payout with an array of transfers and a unique X-Idempotency-Key.
  2. 2 Transfers are validated (address format, testnet bit on mainnet, USDT wallet present) and written to SQLite as queued.
  3. 3 The batch window (BATCH_WINDOW_MS) accumulates concurrent requests, then signs one Highload Wallet v2 external message.
  4. 4 Signed bytes are sent to TON Center sendBoc. Status becomes sent; a webhook fires immediately.
  5. 5 After CONFIRM_DELAY_MS (default 12 s) the poller walks getTransactions pages until it finds the message hash. Status becomes confirmed.
  6. 6 Webhook outbox delivers the final event. Records are archived after 30 days.
