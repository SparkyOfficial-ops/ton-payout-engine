# ton-payout-engine

Шлюз массовых выплат TON. Пачку отправляет `CtonChainSender` через соседний `cton-sdk`.

Из SDK используются только:

- `com.cton.api.TonApiClient` — баланс и `sendBoc`
- `com.cton.contract.HighloadWallet` — сборка и подпись Highload Wallet v2
- `com.cton.contract.BulkTransfer` — один получатель внутри пачки
- `com.cton.sdk.Address` и `com.cton.sdk.Crypto.PrivateKey` — адрес и ключ Ed25519

`Cell`, `Boc` и `HashmapE` вызываются внутри `HighloadWallet`, отдельно их подключать не нужно. Нативная библиотека `cton-sdk-core` нужна в момент подписи. NFT, Jetton и обычные Wallet V3/V4 этому сервису не нужны.

## Запуск

```text
mvn -f ../cton-sdk-main/pom.xml install -DskipTests
mvn clean package
java -jar target/ton-payout-engine-0.1.0-SNAPSHOT.jar
```

Ключ API задаётся переменной `PAYOUT_API_KEY` (или `auth.apiKey` в `src/main/resources/application.properties`). Файл ключа кошелька лежит только на сервере, путь — `WALLET_KEY_PATH`. В репозиторий его не класть.

## API

Заголовок: `X-Api-Key`. Для выплаты обязателен `X-Idempotency-Key`: уникальный id операции на стороне бота. Повтор с тем же ключом и тем же телом не создаёт вторую пачку и возвращает текущий статус (`200`). Другое тело с тем же ключом отвечает `409`.

`POST /api/v1/payout`

```json
{
  "transfers": [
    {"to": "EQ...", "amount": "5", "comment": "vasya"},
    {"to": "EQ...", "amount": "2", "comment": "petya"},
    {"to": "EQ...", "amount": "10", "comment": "masha"}
  ]
}
```

`amount` — сумма в TON. `amountNano` по-прежнему принимается, если сумма уже в нанотонах. Ответ `202` содержит `batchId`. Адрес проверяется до записи в базу: user-friendly base64url с CRC16 или raw `workchain:64hex`, workchain от -128 до 127. Опечатка даёт `400` и не попадает в общий батч. Уже сохранённая битая заявка помечается `failed` одна, соседние переводы этого окна уходят как обычно.

Перед ответом переводы записываются в SQLite (`PAYOUT_DB_PATH`, по умолчанию `data/payout.db`) со статусом `queued`. После перезапуска такие переводы снова попадают в автобус. Статус `sending` означает, что отправка уже началась: эти строки после падения процесса сами не отправляются повторно. Хэш внешнего сообщения считается локально и записывается в базу до `sendBoc`. Если узел ответил ошибкой, те же байты отправляются ещё два раза. Если процесс умрёт, пока байты уже в сети, пачка остаётся `sending` с этим хэшем, а не `failed`.

Движок копит переводы `BATCH_WINDOW_MS` (по умолчанию 2500 мс) или до `BATCH_MAX_SIZE` (254) и отправляет их одной транзакцией Highload Wallet v2. Хэш из `sendBoc` означает только приём в мемпул: пачка становится `sent`. Через `CONFIRM_DELAY_MS` (по умолчанию 12 секунд) фоновый опрос один раз за тик забирает `getTransactions` кошелька и по этому списку проверяет все ожидающие пачки. Если хэш входящего сообщения есть в блоке, статус становится `confirmed`. В `query_id` внешнего сообщения записывается срок на минуту короче `MESSAGE_TTL_MS`: по умолчанию сообщение живёт 15 минут. Опрос не ставит `failed`, пока эти 16 минут не прошли, даже если хэша ещё нет в `getTransactions`. Пустой `sent_at` считается от `created_at`: каждый промах опроса больше не обнуляет срок. Иначе бот повторит выплату, а первое сообщение позже попадёт в блок.

Вебхук уходит на `sent` и ещё раз на `confirmed`:

```json
{"batchId":"...","status":"confirmed","count":3,"txHash":"...","error":null}
```

`GET /api/v1/status/{batchId}` показывает `queued`, `sending`, `paused`, `sent`, `confirmed` или `failed`.

Перед отправкой движок сравнивает баланс с суммой переводов плюс комиссию сети: `FEE_RESERVE_NANO` (0.05 TON на внешнее сообщение) и `FEE_PER_TRANSFER_NANO` (0.008 TON на каждое внутреннее). Для 254 переводов это 2.082 TON, а не 0.05. Если денег меньше, пачка становится `paused`, в сеть ничего не уходит, и на `ALERT_URL` отправляется алерт. Проверка повторяется через `PAUSE_RETRY_MS`.

Если пачка осталась в `sending` дольше `SENDING_STALE_MS` (5 минут) и в ней не осталось `queued` переводов, движок её не переотправляет. Хэш, который уже лежит в блоке, сразу переводит пачку в `confirmed`. Хэш, которого нет, или который не сохранился, переводит её в `failed` только после `MESSAGE_TTL_MS`. Повтор такой выплаты делается новым `X-Idempotency-Key`, а если хэша не было — сначала сверяется история кошелька. `POST /api/v1/recovery` запускает ту же проверку и не трогает `sending` младше пяти минут.

Раз в сутки пачки `confirmed` и `failed` старше `HOUSEKEEPING_RETENTION_MS` (30 дней) переносятся из `payout.db` в соседний `payout-archive.db`. `queued`, `paused`, `sending` и `sent` остаются на месте. Тот же `X-Idempotency-Key` после архивации возвращает прежний статус и вторую выплату не создаёт. Строки не удаляются совсем: отдельного подтверждения, что бот принял вебхук, нет, поэтому история остаётся в архиве.

`GET /api/v1/balance`

`GET /health` без ключа. Ответ `200`, когда `SELECT 1` к SQLite проходит и на месте адрес с файлом ключа. Если база недоступна или ключ пропал, ответ `503`: Docker и Kubernetes не пускают на процесс трафик. Запросы принимает пул из 16 потоков, поэтому проверка здоровья не ждёт ответ ноды на `/api/v1/balance`.

Нужны `WALLET_ADDRESS` и файл ключа (`WALLET_KEY_PATH`: 32 байта, 64 hex-символа, base64 или мнемоника). Без них пачка получает статус `failed` и в сеть не уходит. `txHash` — это hash внешнего сообщения из ответа TON Center `sendBoc`. Подтверждение сравнивает его только с `in_msg.hash` или `in_msg.body_hash`. Hex от SDK и base64 от Toncenter — это одни и те же 32 байта. `transaction_id.hash` — это хэш самой транзакции, он не используется. В лог пишется сырой JSON первой транзакции из `getTransactions` и обе строки `in_msg`, чтобы их можно было сверить с хэшем `cton-sdk` посимвольно.
